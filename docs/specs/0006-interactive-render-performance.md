# Interactive render performance

## Problem Statement

Large SiYuan documents can make Linkmark's Interactive render pipeline perform
substantial main-thread work while a user types, pastes, rewrites, or removes
links. Wall-clock performance depends on the browser and device, so CI timing
assertions would be unstable, but the algorithmic boundaries and observable
render behavior still need deterministic regression coverage.

## Solution

Keep discovery local for ordinary input, coalesce render work, publish Icon
rules at most once per batch, and reconcile rules only for Present scopes. The
standard Large-document performance scenario contains 2,000 external-link
representations across 500 Link scopes. A test-only 10,000-entry cache fixture
proves that rule output stays bounded by those Present scopes rather than the
complete cache.

The repository script generates the standard document on demand for manual
browser profiling. The manual targets remain an Incremental interaction P95 of
at most 8 milliseconds, a Full discovery of at most 50 milliseconds, and Rule
freshness of at most 300 milliseconds. These values are profiling goals, not CI
gates or cross-device promises.

Linkmark does not provide an in-app performance trace, runtime fixture cache,
diagnostic setting, or trace RPC. Manual measurements use ordinary browser
profiling tools against the real Frontend cache state.

## User Stories

1. As a user editing a large document, I want ordinary input to remain responsive.
2. As a user changing one link, I want Linkmark to inspect only the relevant local region.
3. As a user with repeated, domain, route-specific, or Pinned links, I want existing icon precedence preserved.
4. As a maintainer, I want a deterministic 2,000-link and 500-scope scenario that is generated outside the tracked source set.
5. As a maintainer, I want structural tests instead of CI timing thresholds.
6. As a maintainer, I want measured performance claims recorded with source, Linkmark, SiYuan, Chromium, device, baseline, candidate, and limitation details.
7. As a maintainer, I want new indexes, copied state, scheduling changes, or material memory-for-CPU trade-offs selected only after profiling identifies a hotspot.
8. As a maintainer, I want production-derived performance state to scale with Present scopes and target at most 5 MiB in the standard scenario.

## Implementation Decisions

- The scope is the Interactive render pipeline: mutation scheduling, link discovery, Icon rule reconciliation, and runtime stylesheet publication.
- Plugin startup, Cache snapshot transport, favicon resolution, network retrieval, Cache persistence, and private icon serving are non-regression boundaries.
- Ordinary input uses local discovery. Link removal or URL identity changes may escalate to Full discovery so departed rules are evicted.
- Render work coalesces discovery, rebuild, and publication requests into one batch with at most one stylesheet publication.
- Local reconciliation streams discovered scopes. It returns the previous Map when every candidate is a no-op and copies once on the first effective upsert.
- Full reconciliation computes a complete replacement and removes scopes that are no longer Present.
- The standard document is generated by `scripts/generate-perf-scenario.mjs` and contains exactly 2,000 links across 500 scopes.
- The 10,000-entry cache is a test-only fixture. It is never imported by plugin runtime code, bundled into artifacts, exposed in settings, or written to Cache authority state.
- Manual profiling uses browser tooling and the real cache. Numeric results must be interpreted with their recorded environment.
- Prefer deletion, existing work coalescing, and narrower discovery before adding state or abstractions. Performance tooling adds no runtime dependency.
- Structural optimizations may proceed without manual timing when the reduced work follows from the algorithm, no persistent state is added, and behavior remains covered.
- Documentation must not translate structural evidence into an unmeasured latency, percentile, or percentage claim.

## Testing Decisions

- The highest automated seam is one Frontend render-work flush supplied with a deterministic executor.
- Tests prove local discovery, work coalescing, one publication per batch, Full-discovery supersession, and departed-scope eviction.
- Local reconciliation tests treat Map identity as observable: no-op work returns the same Map; effective upserts return a new Map without mutating the input.
- Reconciliation against a test-only 10,000-entry cache produces exactly 500 rules for the standard Present scopes.
- Tests preserve selector coverage, domain and route precedence, Pinned behavior, freshness, automatic-fetch pause, and fail-open rendering.
- The generator test proves exactly 2,000 links and 500 distinct scopes without committing the generated Markdown artifact.
- Build-boundary and package tests prove no trace control, trace RPC, trace logger, or runtime performance fixture exists in development or production artifacts.
- Manual profiling is the only evidence for the 8 millisecond, 50 millisecond, 300 millisecond, and 5 MiB targets.

## Out of Scope

- Browser, Docker, or SiYuan end-to-end automation and CI timing benchmarks.
- An in-app trace, runtime fixture overlay, diagnostic setting, telemetry, analytics, remote logging, or performance dashboard.
- Changing Cache policy, Display preferences, Link scope identity, pinned-icon behavior, cache freshness, route precedence, automatic-fetch behavior, or fail-open rendering.
- Committing to a persistent DOM index before profiling identifies Full discovery as a material hotspot.
- General UI redesign, release publication, version changes, or unrelated refactors.

## Further Notes

- Editor responsiveness is the primary outcome; favicon download speed is not a proxy for it.
- The 250 millisecond discovery debounce and subsequent render batch are part of current Rule freshness behavior.
- No ADR is required because the evidence policy and copy-on-write optimization are reversible and add no durable architectural state.
