# Publish incremental cache change events instead of cache snapshots

Linkmark broadcasts `{revision, upserts, removed}` cache change events instead of the complete cache on every mutation, because at the targeted thousand-to-ten-thousand entry scale a full-snapshot broadcast on every committed batch makes serialization, RPC transfer, and frontend rule rebuilding O(cache size) per change. The kernel Cache authority owns a strictly increasing per-process Cache revision, increments it once per committed persistence batch (keeping the existing batch coalescing), and a Frontend client that observes a revision gap refetches `cache.snapshot` to recover; a fresh client always snapshots at startup, so the process-local revision resetting on kernel restart is harmless because every window reloads and re-snapshots. This was chosen over per-key-only increments without revision numbers, which cannot detect missed or reordered events in suspended windows, and over retaining full snapshots, which keeps the O(n) per-change cost the design exists to remove.

# Look up private icons through a lossless iconId encoding

Private icon requests resolve an iconId to its cache entry in O(1) without a maintained index: the iconId embeds the scope key encoded losslessly (base64url, whose alphabet already matches the private-route regex), so the kernel parses the key back out and verifies `cache[key].iconId === iconId` before serving, falling back to the former linear scan only for legacy-format iconIds. This was chosen over a `Map<iconId, entry>` that must stay synchronized at every cache mutation site and over a key-based private route, which would keep the same URL across icon refreshes and let browsers serve stale icons for the full `max-age=86400` instead of cache-busting on every new icon.
