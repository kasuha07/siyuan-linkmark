# Publish incremental cache change events instead of cache snapshots

The Frontend synchronization and event-payload portions of this decision are
superseded by ADR 0015. Its fixed-window persistence batching, no-op mutation,
commit-before-notification, and failure-boundary decisions remain in force.

Linkmark broadcasts `{epoch, revision, upserts, removed}` cache change events instead of the complete cache on every mutation, because at the targeted thousand-to-ten-thousand entry scale a full-snapshot broadcast on every committed batch makes serialization, RPC transfer, and frontend rule rebuilding O(cache size) per change. The kernel Cache authority owns a strictly increasing per-process Cache revision, increments it once per committed persistence batch (keeping the existing batch coalescing), and a Frontend client that observes a revision gap refetches `cache.snapshot` to recover. `cache.snapshot` returns `{cache, revision, epoch}`, and the client adopts that revision as its baseline before consuming events: events at or below the snapshot revision are already contained, the next consecutive revision applies, and any other gap refetches again — so a commit between the snapshot response and the subscription bind can never be misapplied as the next first event. Because the revision is process-local and the kernel plugin can reload without reloading any window, every event and snapshot also carries the per-process Cache epoch; a client that sees an epoch different from its baseline discards its revision and refetches, so a restart resets the stream without leaving surviving windows permanently blind to low revisions. A lookup response whose epoch differs from the client baseline is rebaselined cursor-only: the client adopts the response cursor as its new baseline, discards the response's entries, and re-issues the lookup under that baseline, so a previous-epoch response can never overwrite current state and the refresh converges on a subsequent matching response. This was chosen over per-key-only increments without revision numbers, which cannot detect missed or reordered events in suspended windows, over retaining full snapshots, which keeps the O(n) per-change cost the design exists to remove, and over persisting the revision across restarts, which trades a hot-path storage dependency for a problem the epoch marker solves locally.

The performance boundary is the Incremental cache hot path, not fully incremental persistence. This ADR's original delta transport was superseded by the compact cursor plus authoritative lookup/query design in ADR-0015 and SPEC-0008: Frontend clients no longer receive or apply complete-cache deltas, and cache-management pages are served from a revision-cached kernel index.

The Frontend cache view remains a mutable `Record<string, CacheEntry>` matching the snapshot and event RPC shapes; converting it to `Map` would widen the representation boundary without removing additional hot-path work. Event application validates the complete delta before mutation, retains only the prior values for affected keys, then applies valid upserts and removals in place. Binding synchronization consumes that sparse before/after change rather than a full prior cache object. The existing last-seen Cache revision remains the sole event-stream cursor, while a separately maintained entry count replaces repeated full-cache enumeration for cache-count display.

Every explicit cache mutation RPC (`cache.remove`, `cache.pin`, `cache.pin-url`, `cache.clear`, and `cache.clear-generated`) returns a Cache mutation receipt. A committed receipt carries the exact Cache change event also sent to subscribers; the initiating Frontend client applies it through the same revision-checked event path, making whichever of RPC response or broadcast arrives second an ignored duplicate. A no-op returns `unchanged` with the authority's current epoch and revision without incrementing the revision: the caller may apply the known absence only when that cursor matches its baseline, and otherwise recovers through `cache.snapshot`. This keeps broadcasts as cross-client dissemination while giving the initiating client a deterministic result without a post-mutation snapshot.

Cache persistence commit and subscriber notification are separate outcomes. Once the cache index write succeeds, the mutation is committed and its receipt remains successful; a failure while broadcasting that committed event is logged and does not roll back the index or turn the RPC into a failure. Payload or index-write failure still aborts the mutation before its receipt and event are published. Clients that miss a broadcast recover through the existing Cache revision and Cache epoch checks.

Resolved entries use a fixed 32-millisecond Cache persistence batch window beginning when the first result is staged. The timer is not reset by later arrivals, so sustained completions cannot postpone persistence indefinitely; results arriving while a batch is flushing enter the next window. Explicit cache mutations remain immediate and retain generation invalidation against staged resolutions. A resolved batch remains atomic at the index boundary and publishes one event only after its index write succeeds.

Bulk workspace cache operations are intentionally proportional to the entries they remove rather than classified as ordinary single-entry hot-path mutations. `cache.clear` and `cache.clear-generated` may enumerate affected entries to invalidate tasks, construct `removed`, and delete payloads, but they must not create full before/after copies merely to rediscover that delta. An empty bulk operation is `unchanged`: it performs no index write, does not increment the revision, and sends no event.
