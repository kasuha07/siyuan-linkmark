# Publish incremental cache change events instead of cache snapshots

Linkmark broadcasts `{epoch, revision, upserts, removed}` cache change events instead of the complete cache on every mutation, because at the targeted thousand-to-ten-thousand entry scale a full-snapshot broadcast on every committed batch makes serialization, RPC transfer, and frontend rule rebuilding O(cache size) per change. The kernel Cache authority owns a strictly increasing per-process Cache revision, increments it once per committed persistence batch (keeping the existing batch coalescing), and a Frontend client that observes a revision gap refetches `cache.snapshot` to recover. `cache.snapshot` returns `{cache, revision, epoch}`, and the client adopts that revision as its baseline before consuming events: events at or below the snapshot revision are already contained, the next consecutive revision applies, and any other gap refetches again — so a commit between the snapshot response and the subscription bind can never be misapplied as the next first event. Because the revision is process-local and the kernel plugin can reload without reloading any window, every event and snapshot also carries the per-process Cache epoch; a client that sees an epoch different from its baseline discards its revision and refetches, so a restart resets the stream without leaving surviving windows permanently blind to low revisions. This was chosen over per-key-only increments without revision numbers, which cannot detect missed or reordered events in suspended windows, over retaining full snapshots, which keeps the O(n) per-change cost the design exists to remove, and over persisting the revision across restarts, which trades a hot-path storage dependency for a problem the epoch marker solves locally.
